# 项目分析方法论

配合 `SKILL.md` 第 2 步。目标：在动手设计前，先准确、高效地理解项目现状。综合自业界常见的代码库理解方法（自顶向下 / 自底向上 / 混合）与 C4 模型。

## 三种进入方式

| 方式 | 做法 | 适用 |
|------|------|------|
| **自顶向下** | 从入口/启动点出发 → 目录与模块结构 → 依赖关系 → 主要数据流 | 想快速建立全局地图 |
| **自底向上** | 从核心文件/关键类/热点函数出发，往上还原它服务的业务与设计 | 已知痛点/要改的具体位置 |
| **混合（推荐）** | 先自顶向下拿到骨架，再对关键模块自底向上钻透 | 多数真实场景 |

## C4 分层视角（由粗到细看架构）

1. **System Context**：系统与外部用户/系统的关系（最外层）。
2. **Container**：可独立部署/运行的单元（服务、前端、DB、队列等）及其交互。
3. **Component**：容器内部的主要模块/组件与职责。
4. **Code**：类/函数级细节（通常按需，不必全画）。

分析时至少产出 Context 与 Container 两层的认知，用 mermaid 画出来。

## 分析清单（要摸清的事实）

- **入口与启动**：程序从哪开始，如何装配/初始化。
- **目录/模块结构**：各目录职责，核心模块边界。
- **依赖关系**：内部模块依赖 + 外部依赖（库、服务、DB、第三方 API）。
- **数据流**：一个典型请求/任务从入口到出口如何流转。
- **数据模型**：核心实体、存储方式。
- **技术栈**：语言、框架、构建、部署方式。
- **横切**：鉴权、配置、日志/监控、错误处理。
- **痛点/风险**：重复、耦合、性能瓶颈、缺测试、坏味道。

## 5 层理解（自检你到了哪一层）

1. 能跑起来、知道大概做什么。
2. 知道目录结构与主要模块职责。
3. 能追一条完整数据流/调用链。
4. 理解关键设计取舍与约束（为什么这样做）。
5. 能预判"改动某处会影响哪里"，可安全演进。

设计方案至少要建立在第 3–4 层理解之上。

## 工具建议

- 有代码知识图谱/AST 工具（如 codegraph、tree-sitter）时优先用，快速拿符号与调用链；否则用搜索（Grep/Glob）+ 读关键文件。
- 大项目：把分析放进 subagent 跑，只带回结论。
- 只读事实，不臆测；不确定的点标注为"待确认"，进入设计阶段的"未决问题"。
