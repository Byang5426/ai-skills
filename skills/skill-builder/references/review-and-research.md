# 评审：适合性判断 + 联网参考

配合 `SKILL.md` 第 0 步使用。目标：在动手前判断"该不该做成 skill"，并在必要时借鉴网上已有实现。

## 一、适合性判断（该不该做成 skill）

先确认需求匹配 skill 的本质：**可复用的能力/知识/工作流**。若更符合其他机制，建议用户改用它，并说明理由。

| 需求特征 | 更合适的机制 | 原因 |
|----------|--------------|------|
| 可复用的工作流、领域知识、固定输出格式 | **skill** | skill 就是为"把专门知识/流程固化并按需加载"设计的 |
| 需要独立上下文窗口、扮演某角色、可被主控派活 | **subagent** | skill 不能自己调用工具或派活；角色分工要用 subagent |
| 只是全局约束、编码风格、语气偏好 | **rule** | 规则常驻注入，不需要按需加载的文档体 |
| 只是一段固定触发的指令 | **command** | 轻量、直接，不值得建一个 skill 目录 |
| 需要连接外部系统 / API / 数据库 | **MCP** | 对接外部能力是 MCP 的职责 |
| 一次性任务、明显不会复用 | **直接做** | 复用价值为零时，建 skill 是过度工程 |

判断产出（写给用户一句话即可）：
- 适合 → "这个场景适合做成 skill，继续。"
- 不适合 → "建议用 <机制> 而不是 skill，因为 <原因>。" 然后停下等用户确认。

> 边界情况：若同时涉及"角色分工 + 可复用知识"（如多 agent 协作），通常是 **subagent 承载角色 + skill 承载知识** 的组合，而非单个 skill。

## 二、联网参考（可选，按需触发）

**默认关闭。** 仅当满足以下任一条件才联网：

1. 场景对你**陌生**、没有把握怎么组织；
2. 领域**专业性强**（特定框架/协议/行业规范），存在成熟约定值得遵循；
3. 用户**明确要求**参考现有实现。

标准/常见场景（commit message、代码审查、PDF 处理等）直接走 [authoring-rules.md](authoring-rules.md)，不要联网。

### 检索方法

优先用 firecrawl（若不可用则用可用的联网工具）。围绕"这类 skill/agent 别人怎么建"检索，例如：

```bash
firecrawl search "<领域/场景> Claude Code skill OR Cursor skill example SKILL.md" --limit 6 -o .firecrawl/s-skill-ref.json --json
```

- 优先看官方文档与高星仓库里的 `SKILL.md` 真实范例。
- 提取"目录结构、frontmatter 写法、章节组织、约定"，而非照抄内容。

### 用联网结果时的纪律

- **过滤噪音**：网上结果质量参差、可能过时；只采纳与官方规范一致、且明显提升质量的做法。
- **不外泄依赖**：联网只用于"设计参考"，生成的 skill 本身不得依赖联网才能工作。
- **成本意识**：联网增加时间与 token；拿到足够信号即停，不要无限深挖。
- **回落**：联网失败/无有用结果时，直接按官方规范继续生成，不阻塞主流程。
