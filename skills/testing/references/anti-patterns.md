# 测试反模式 + 修法

配合 `SKILL.md`。识别这些"测试坏味道"，并按修法处理。

| 反模式 | 表现 | 修法 |
|--------|------|------|
| **过度 mock** | 一个测试 mock 一大堆，测的其实是"mock 有没有被调用" | 只 mock 外部副作用；自己的逻辑用真实对象。非得狂 mock → 先改设计（解耦） |
| **测实现细节** | 断言私有方法/内部字段/调用次数；一重构就红 | 只断言对外可观察行为/输出/契约 |
| **flaky（不稳定）** | 时过时不过 | 去掉 `sleep` 硬等待改条件等待；注入时钟/随机；隔离共享状态；不依赖执行顺序 |
| **assertion roulette** | 一个测试一堆无关断言，挂了不知哪条 | 一个测试聚焦一个行为；拆分或参数化；给断言加信息 |
| **断言过弱** | 只断"没抛异常""不为 null" | 断言具体期望值/状态/副作用 |
| **快照滥用** | 大快照当断言，改动全靠"更新快照"划过 | 快照只用于稳定的小结构；关键行为写显式断言 |
| **一个测试测太多** | 名字含 and、几十行、多个 Act | 一测一行为，名字写清"在什么条件下期望什么" |
| **测试互相依赖** | 必须按顺序跑、共享全局状态 | 每个测试自带 setup/teardown，独立可单跑 |
| **为不可能的情况写测试** | 防御性测一堆不会发生的分支 | 删掉；测真实契约与已知风险，避免过度工程 |
| **没有失败先验证** | 直接写"绿"测试，其实断言写错也发现不了 | TDD 先让它红一次，确认测试真的会失败 |

## 快速自检（写完一个测试问自己）

- 它测的是**行为**还是**实现**？重构会不会误伤？
- **失败信息**能不能一眼看出哪出错？
- 换台机器/换个顺序跑还稳吗？（Isolated + Repeatable）
- 有没有覆盖**至少一个 unhappy path**？
- 这个 mock **真有必要**吗？
